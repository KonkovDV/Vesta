# Исправленный план работ для ИИ-агента — Vesta / MicroPhoenix kernel

Документ для ИИ-исполнителя (Claude Code, Codex, Cursor и т.п.) и человека, который его ведёт. Опирается на `01_AUDIT_REPORT_RU.md` и `03_findings.json`.

## 0. Промпт для запуска ИИ (скопируйте целиком)

```text
Ты работаешь в репозитории KonkovDV/Vesta (пакет microphoenix). Базовый коммит e6814bb.
Вход: каталог vesta-audit-2026-10-24/ (отчёт 01, план 02, реестр 03, patches/).

1. Выполни фазу 0 плана 02_WORK_PLAN_FOR_AI.md буквально и покажи вывод команд.
2. Затем бери задачи из разделов 4–5 этого плана строго по порядку.
   Одна задача = одна ветка = один PR. Не начинай следующую, пока у текущей не выполнены
   все acceptance-критерии и не зелёные: npm run typecheck, npm test, npm run test:integration.
3. Для каждой находки сначала напиши тест, который падает на текущем коде, покажи падение,
   затем исправь и покажи прохождение. Без падающего теста исправление не принимается.
4. Не ослабляй проверки, не удаляй тесты, не отключай правила, не меняй claims в docs без теста.
   Если задача требует решения владельца (помечено decision: owner) — остановись и спроси.
5. После каждой задачи обнови KNOWN_ISSUES.md (статус MP-K), docs/claims.md (если меняется
   заявление), CHANGELOG.md. Пиши коротко и фактами, в стиле существующих файлов.
6. Никаких секретов в коде и логах. Никаких новых строковых DI-токенов (см. T2.3).
```

## 1. Правила работы (обязательные)

1. **Тест до исправления.** Каждая задача начинается с теста, воспроизводящего дефект (юнит или интеграционный). В PR — вывод «до» (падение) и «после».
2. **Маленькие PR.** ≤ 400 строк изменений без учёта lock-файла и сгенерированного; иначе разбить.
3. **Заявления только с доказательством.** Любая строка в README/`docs/claims.md`/`KNOWN_ISSUES.md` указывает тест или файл доказательства.
4. **Безопасные умолчания.** Новая настройка по умолчанию — самая строгая; ослабление — явным флагом с комментарием «почему».
5. **Совместимость.** Изменение `runKernel`, `KernelExtension`, порядка миграций или `exports` — мажорная версия (см. `RELEASE_POLICY.md`); иначе минорная.
6. **Зависимости.** Новые — только с обоснованием, точной версией и `npm audit --omit=dev` = 0. Install-скрипты — только в allowlist.
7. **Стоп-условия.** Остановиться и спросить владельца, если: задача удаляет функциональность продукта (healthcare/HR/sales), меняет модель угроз, требует внешнего сервиса или ломает обратную совместимость.

## 4. Фаза 1 — P0, до 2 недель

### T1.1 Надёжный транспорт событий (V-06, MP-K22)
- **Цель:** событие, принятое outbox, гарантированно доходит до каждого потребителя хотя бы раз.
- **Шаги:** (1) порт `IEventBus` без изменений; адаптер `RedisStreamsEventBus`: `XADD stream:<type> MAXLEN ~ N`, группа на потребителя (`XGROUP CREATE ... MKSTREAM`), `XREADGROUP` + `XACK` после обработки, `XAUTOCLAIM` для зависших, DLQ-поток после N доставок; (2) идемпотентный потребитель на таблице `processed_events (consumer, event_id)` — она уже есть в `001_consolidated.sql`; (3) выбор транспорта `EVENT_BUS_TRANSPORT=streams|pubsub`, по умолчанию `streams` в новой мажорной версии; (4) альтернатива для внутренних потребителей — чтение журнала через `getCommittedEventsAfter` с хранимым курсором.
- **Приёмка:** интеграционные тесты: потребитель выключен во время публикации → после включения получает событие; падение потребителя до `XACK` → повторная доставка; дубликат не обрабатывается дважды (`processed_events`). Обновить C5.
- **Риски:** память Redis — `MAXLEN ~`; порядок внутри агрегата — ключ потока/шардинг по `aggregate_id`.

### T1.2 Все читатели журнала — в порядке коммитов (V-17, MP-K23)
- **Шаги:** перевести `SemanticEmbeddingWorker` и прочих читателей `getEventsByGsnRange` на `getCommittedEventsAfter` с курсором `(txId, gsn)` в таблице курсоров; `idle_in_transaction_session_timeout` для ролей приложения; метрика «отставание читателя» (`now() − время последнего прочитанного`).
- **Приёмка:** тест из `tests/integration/event-commit-order.test.ts` для воркера; grep: `getEventsByGsnRange` вызывается только из диагностик.

### T1.3 Убрать DDL из старта приложения (V-28, MP-K24)
- **Шаги:** перенести 7 таблиц, создаваемых при старте (`error_graph_*`, `learning_*`, HNSW-индексы), в `004_runtime_tables.sql`; `initialize()` в event store / outbox / MAS / memory stores — только проверка наличия схемы (ошибка с понятным текстом «примените миграции»); флаг `DB_RUNTIME_DDL=false` по умолчанию.
- **Приёмка:** чистая БД → `migrate` → старт без единого `CREATE`/`ALTER` в логе запросов (`log_statement=ddl`); 20 параллельных стартов без ошибок `pg_type_typname_nsp_index`.

### T1.4 Авторизация продуктовых маршрутов (V-19, MP-K32) — `decision: owner`
- **Вопрос владельцу:** остаются ли `sales`/`hr`/`healthcare` в ядре (см. T2.1). Если да — scope `sales.*`, `hr.*`, `healthcare.read|write` на каждый маршрут через `requireScope`; tenant из ключа.
- **Приёмка:** для каждого маршрута тест: ключ без scope → 403; с scope → не 403.

### T1.5 MCP HTTP-сервер (V-20, MP-K31) — `decision: owner`
- **Вариант A (рекомендуется):** удалить монтирование из `AppServer`, оставить сервер как библиотеку для продукта. **Вариант B:** смонтировать до 404 через `HttpRouteRegistrar`, профиль инструментов — из scope ключа, OAuth 2.1 по спецификации MCP 2025-11-25.
- **Приёмка (B):** `initialize` + `tools/list` отвечают; набор инструментов зависит от scope, а не от URL; тест на `/api/mcp/researcher-x/...`.

### T1.6 Оптимистичная блокировка на пути outbox (V-38)
- **Шаги:** `saveEventsWithOutbox(events, { expectedAggregateVersion })`: при несовпадении — `ConcurrencyError`, без повторной перенумерации; повтор с перенумерацией только без ожидаемой версии.
- **Приёмка:** два конкурентных сохранения с одной ожидаемой версией → одно успешно, второе `ConcurrencyError`.

### T1.7 Защитные гейты CI
- **Шаги:** job `resolve-all`: поднять ядро с `USE_MOCK_AI=true` и разрешить все токены (`probes/resolve-all.cjs`), бюджет отказов — текущий, только уменьшение; job `routes-auth`: обход маршрутов без ключа (`probes/routes.cjs`), список открытых маршрутов — фиксированный allowlist.
- **Приёмка:** добавление незащищённого маршрута или неразрешимого токена валит CI.

## 5. Фаза 2 — P1, архитектура, 2–6 недель

### T2.1 Сократить ядро до границы ADR-0003 (V-41, V-31, V-33, MP-K36–K38) — `decision: owner`
- **Шаги:** (1) инвентарь модулей по `evidence/layers.json` и графу загрузки; (2) вынести в отдельные пакеты или репозитории продуктов: `healthcare` (MRI, ingestion-воркеры), `hr`, `sales`, `research`, x402/A2A-платежи, «singularity/dream_state», graph-memory/Kuzu, OpenClaw-мост; (3) удалить заглушки `@sota-stub` (36 маркеров, 17 файлов) и защитные компоненты, которых никто не вызывает, — либо подключить их на путь запроса с тестом; (4) worker с `new Function` — удалить или перевести на `IProcessContainer`.
- **Целевые метрики:** ≤ 40 тыс. строк в ядре; ≤ 30 production-зависимостей без нативных модулей; git-установка ≤ 60 с и ≤ 200 МБ; RSS в простое ≤ 150 МБ; 0 зарегистрированных, но неразрешимых токенов.
- **Приёмка:** метрики измерены в CI; все 66 текущих тестов зелёные; продукт-пример (README) собирается на новом ядре.

### T2.2 Явная идемпотентность вместо масок имён (V-03)
- **Шаги:** метаданные `aspectOptions.metadata.idempotent = true` или декоратор `@Idempotent()`; `RetryAspect` по умолчанию не повторяет ничего без пометки; пометить только реально идемпотентные чтения; идемпотентные ключи для записей во внешние системы (x402 — `Idempotency-Key`).
- **Приёмка:** тест: непомеченный метод не повторяется ни при какой ошибке; помеченный — только при транзиентной.

### T2.3 Типизированный DI (V-40, V-12)
- **Шаги:** `InjectionToken<T>` для всех 366 токенов (codemod по `DI_TOKENS.ts`); `resolve<T>(token: InjectionToken<T>)`; ESLint-правило, запрещающее строковый литерал в `register/resolve`; убрать inversify-декораторы или собственный контейнер — оставить один механизм.
- **Приёмка:** `tsc` ловит несовпадение типа токена (тест-фикстура с намеренной ошибкой); 0 строковых литералов в `resolve(`.
